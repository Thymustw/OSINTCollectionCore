# 文件網站寫作規範

這份規範給撰寫 `docs-site/docs/` 底下任何頁面的人（包括 AI agent）。
目標讀者是**從沒碰過這個專案的外部使用者**，其次是想了解架構的開發者。

## 1. 語言

- 一律**繁體中文（台灣用語）**。
- 技術術語保留英文，但**第一次出現時用中文說明**：
  「Source（資料來源）」、「JWT（一種 API 憑證格式）」。
- **不要**整句英文、不要英文標題、不要中英混雜的句子（例如「這個 feature 會 trigger 一個 job」）。
- API 路徑、欄位名、指令、檔名用 `程式碼格式`，照原樣不翻譯。

## 2. 內容取捨：這是產品文件，不是內部紀錄

- **寫：**這個功能是什麼、能做什麼、怎麼用（附可以直接複製執行的指令）、會得到什麼結果、常見錯誤。
- **不寫：**開發過程、內部決策爭論、ADR 編號、「V0.2 Phase 3 Step B」這類內部進度代號、
  commit hash、測試名稱、技術債編號（T1–T24）。
- 限制要**照實寫**，但用使用者看得懂的方式：
  - 不好：「graph-worker 的 apply_relationship 對 SkippedNonEntity 直接 return」
  - 好：「圖上只顯示實體和實體之間的關係，文件本身不是圖上的節點」
- 不要美化。做不到的事就說做不到。

## 3. 每個指令都必須實測過

- 文件裡出現的每一個 `curl`／指令，**都要實際執行過並確認輸出**。
- 範例輸出要來自實際執行結果（可以刪減，不能捏造）。
- **例外：憑證一律換成假值，絕對不要貼真實輸出。** 實測發出的 API token、JWT、
  密碼、密鑰，即使事後撤銷了也不能出現在文件裡——這個網站會匯出到公開 repo。
  用明顯的假值，例如 `osint_00000000-0000-0000-0000-000000000000.EXAMPLE-SECRET-DO-NOT-USE`，
  對應的 id 也一起換掉。2026-09-30 曾有一把真實 token 被原樣貼進範例，是 gitleaks
  在推送前攔下的——不要依賴事後攔截。
- 環境：服務在 `http://127.0.0.1:18080`，憑證用
  `export TOKEN=$(python3 scripts/dev-token.py)`、`export API=http://127.0.0.1:18080/api/v1`。
- 執行 API 範例時**不要**建立會殘留的資料；需要建立的話，事後清掉。
- **不要**假設讀者有安裝 Rust 或有 `.env` 檔。對外教學一律走 API（容器裡已經在跑）。
  `make run-cli` 需要 Rust 與 `.env`，只能放在「進階／開發者」段落並註明前提。

## 4. 格式

- 頁首一句話說明這頁在講什麼。
- 用 `##` 分節，每節聚焦一件事。
- 多項並列用表格。
- 提示框（Material for MkDocs 語法）：
  - `!!! note` 補充說明
  - `!!! warning` 容易踩的坑
  - `!!! danger` 會造成資料遺失的操作
- 頁與頁之間用**相對路徑**連結（`../reference/api.md`），不要寫絕對網址。
- 不要在頁面裡寫「最後更新日期」或版本號之類會過時的東西。

## 5. 素材來源

- 使用者文件：`docs/user/*.md`（語氣接近，但要檢查是否過時）
- 開發者文件：`docs/developer/*.md`（技術細節正確但語氣內部，需改寫）
- **程式碼是最終依據**。文件跟程式碼衝突時，以程式碼為準
  （路由：`crates/core-api/src/routes.rs`；列舉值：`crates/core-model/src/enums.rs`）。

## 6. 不要碰

- `docs/`（repo 根目錄那個）底下的任何檔案——那是內部文件，另外維護。
- `docs-site/mkdocs.yml` 的 `nav`——頁面清單由主要維護者控制。
