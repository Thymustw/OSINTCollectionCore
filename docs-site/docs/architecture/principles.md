# 設計原則

這一頁說明貫穿整個系統的架構決策：每條規則是什麼、為什麼這樣設計，以及實際怎麼做到的。

---

## 原始證據不可修改

**規則：** 收進來的原始內容不可修改、不可刪除。

**為什麼：** 情報分析的結論需要能追溯到原始依據。如果原始證據被覆寫或刪除，「這個結論的依據是什麼」就無法回答。

**怎麼做到：** 每一筆 RawEvidence 只有 `INSERT`，沒有 `UPDATE`。SHA-256 雜湊值在寫入時計算並儲存，可以隨時驗證內容沒被動過。正規化、去重、抽取這些後續步驟都是在 RawEvidence 之上「衍生」新資料，不修改原件。

---

## PostgreSQL 是唯一真相來源

**規則：** 所有核心資料都以 PostgreSQL 為準。其他儲存（OpenSearch、Neo4j）是可重建的投影，不是真相來源。

**為什麼：** 只有一個真相來源，才能有清楚的一致性保證。投影可能與 PostgreSQL 出現短暫不一致（例如 worker 重啟後有延遲），但只要能從 PostgreSQL 重建，就不會永久遺失資料。

**怎麼做到：** 所有寫入路徑先寫 PostgreSQL，再透過事件觸發投影更新。搜尋索引和關聯圖都提供完整重建指令。

---

## 投影可完整重建

**規則：** OpenSearch 搜尋索引、Neo4j 關聯圖、向量投影，都可以隨時從 PostgreSQL 重建。

**為什麼：** 讓投影格式的升級（例如改 mapping、改圖 schema）不是破壞性操作。刪掉整個索引、從零重建，是合法且有支援的操作路徑。

**怎麼做到：** 每個投影 worker 都有 `--rebuild` 模式，從 PostgreSQL 全量掃描重建，不依賴中間狀態。

---

## 應用程式透過 API 存取，不直連資料庫

**規則：** 所有應用程式只能透過 Core API（`osint-api`）讀寫資料，不直接連 PostgreSQL 或任何其他資料庫。

**為什麼：** 直連繞過了 RBAC 授權、稽核記錄、請求驗證。應用程式一旦直連，就沒有辦法在不修改每個應用程式的前提下統一加強安全控管。

**怎麼做到：** API 在每個請求做身分驗證（JWT）和角色授權（RBAC）。`osint-cli` 是例外：它是本機開發的唯讀工具，直連 PostgreSQL 但沒有寫入能力，且沒有 RBAC，**不用於正式環境**。

---

## 外部內容預設不可信

**規則：** 所有來自外部來源的內容，在驗證之前都視為不可信。收集器預設拒絕私網位址連線，防止 SSRF（伺服器端請求偽造）攻擊。

**為什麼：** SSRF 讓攻擊者能透過系統去存取內網服務。一個收集器如果能被誘導去打 `192.168.x.x` 或 `169.254.169.254`（雲端 metadata API），後果可能很嚴重。

**怎麼做到：** 收集器在實際發出 HTTP 請求前，先解析目標 IP 並比對私網/loopback/link-local 範圍。雲端 metadata 端點（如 IMDS）是硬拒絕，任何設定都無法覆寫。一般私網位址需要 operator 以上的角色明確建立 `NetworkRule` 才能放行，且每條規則都要填核准者與理由。

---

## 事件消費冪等

**規則：** 每個事件消費者都必須能安全地重複處理同一則事件，不產生重複資料或錯誤狀態。

**為什麼：** 網路故障、服務重啟、消費者崩潰都可能讓同一則事件被重新投遞。如果消費者不冪等，重跑就是災難。

**怎麼做到：**
- Entity 和 Relationship 使用 UUID v5（確定性 ID），重複插入靠 `ON CONFLICT DO NOTHING` 處理
- 搜尋索引用 Document ID 當 OpenSearch `_id`，重送是覆寫
- Consumer 在成功處理後才提交 offset，失敗時不提交，確保下次重試

---

## 所有佇列與並發都有上限

**規則：** 任何可以接受外部輸入的子系統，都必須有明確的並發上限和佇列上限。

**為什麼：** 沒有上限的資源申請，讓一個惡意或故障的資料來源能把整個系統拖垮。

**怎麼做到：**

| 子系統 | 控制機制 |
|---|---|
| 收集器 | 全域 Semaphore（`global_inflight`）+ 每個網域上限 |
| 資料庫連線 | SQLx 連線池大小 |
| Broker 消費 | 每個 worker 的並發上限 |
| OpenSearch bulk | bulk 佇列大小 + 並發請求數 |
| Neo4j 寫入 | 寫入並發上限 |
| AI 推論 | Admission Controller 管控（見下方） |

---

## 背壓設計

**規則：** 下游處理跟不上時，上游要能感知並降速，不能讓訊息無限積壓或記憶體無限成長。

**為什麼：** 沒有背壓，一個慢的環節（例如 AI 服務暫時變慢）會讓整個管線的佇列暴增，最終導致 OOM 或資料遺失。

**怎麼做到：** Redpanda 的 consumer lag 會累積作為天然的背壓緩衝。`osint-indexer` 在 bulk lag 超過門檻時，在批次之間插入延遲，避免 OpenSearch 被壓垮。

!!! warning "跨服務自動背壓尚未完整實作"
    目前背壓只在 indexer 內部生效。收集器不會依據下游積壓量自動降低採集速率，
    需要手動調整設定（`tick_secs`、`global_inflight`）。詳見[目前的限制](limitations.md)。

---

## AI 輸出是衍生資料，不能直接覆寫核心判定

**規則：** AI 模型的輸出只能影響「建議」，不能直接覆寫人工確認的判定結果或身分識別決策。

**為什麼：** 語言模型會產生幻覺，且在特定分布外的輸入上可靠性不穩定。讓 AI 輸出直接修改核心資料，會在沒有任何提醒的情況下引入錯誤。

**怎麼做到：** 大多數 AI 輸出產生「候選」或「建議」，需要人工核准。

**唯一的例外：** 實體合併的中間信心分數帶。當兩個實體的相似度落在「不確定」區間（高於低分門檻、低於高分門檻），本地 AI 模型可以做最終確認，系統只取模型輸出的一個布林值（「相同」或「不同」）來觸發自動合併。低分直接判為不同（不需要 AI）、型別不匹配直接拒絕（不需要 AI），只有真正不確定的案例才進 AI。這是刻意的，目的是限制 AI 能影響的範圍。

---

## AI 失敗不阻塞基本流程

**規則：** 本地 AI 服務不可用時，核心的收集、正規化、去重、實體抽取、搜尋等功能繼續正常運作。

**為什麼：** AI 服務需要特定硬體（GPU/VRAM）且可能重啟或更換，不應成為系統的單點故障。

**怎麼做到：** AI 呼叫只在需要「最終信心判斷」的環節發生（實體合併的中間分數帶、STIX 匯入的自動核准評估）。這些環節失敗時，對應的操作會回傳錯誤，但不影響其他流程。收集一筆新文章的完整路徑（收集→正規化→去重→抽取→搜尋索引→圖投影）完全不依賴 AI。

---

## AI 並發由 Admission Controller 管控

**規則：** AI 推論請求依優先權分流，高優先權（互動）保留名額，低優先權（背景）共用佇列，資源壓力升高時低優先權先降級。

**為什麼：** AI 推論消耗大量 VRAM，無限並發會讓所有請求都變慢。互動請求（使用者在等）和背景批次任務需要不同的等待策略。

**怎麼做到：** `AdmissionController` 把請求分為兩個通道：

- **P0（互動）**：獨立保留名額，滿了立刻失敗，不排隊。目前由 `POST /entities/{id}/resolve` 使用。
- **P1–P4（背景）**：共用佇列，依資源壓力訊號動態放行。P3 目前由 STIX 匯入後的自動核准評估使用。

---

## 沒有寫死的密鑰

**規則：** 任何密鑰、密碼、API token 都不能寫死在程式碼或設定檔裡。

**為什麼：** 寫死的密鑰會進版本控制，被所有有倉庫讀取權限的人看到，且旋轉（rotation）需要改程式碼而不是改設定。

**怎麼做到：** 所有需要密鑰的設定項使用 `secret_ref`（指向環境變數或密鑰儲存），不直接填值。CI 有密鑰掃描，攔截寫死的密鑰。
