# 目前的限制

這一頁如實列出系統目前做不到的事、已知的設計邊界，以及各版本的狀態。

**讀這頁的原因**：避免把系統拿去做它設計上不支援的事。每一條限制都是現實，不是待修的 bug，除非另外說明。

## 操作介面

### 沒有網頁操作介面

**現況：** 所有操作透過 REST API 或命令列（`osint-cli`）。唯一能用眼睛看的是 Neo4j 內建的圖資料庫網頁。

**影響：** 不能在瀏覽器裡管理資料來源、審核候選、查看搜尋結果。

**替代做法：** 直接呼叫 API。快速上手指南有完整的 `curl` 範例。`osint-cli` 提供本機唯讀查詢，需要有 Rust 開發環境。

## 關聯圖的範圍

### 圖上只有實體和實體之間的關係，文件不是節點

**現況：** Neo4j 只存 Entity→Entity 的邊。文件和實體的關係（例如文件「提到」某個 CVE）存在 PostgreSQL 裡，查得到，但不是圖上的節點。

**影響：** 不能在 Neo4j 裡做「哪些文件同時提到這兩個 IP」這類跨文件圖查詢，那類查詢要靠搜尋索引或直接查 PostgreSQL。

---

## 實體抽取的範圍

### 不從自由文字辨識人名或組織名

**現況：** 實體抽取靠確定性規則（格式比對）。CVE、IP、網域、URL、Email、雜湊值這類有固定格式的指標可以自動抽出。人名只從文件的「作者」欄位取得。文章內文裡提到的人名和組織名不會被自動識別。

**影響：** 如果你上傳一篇文章，裡面提到「攻擊者來自 Phantom Group」，「Phantom Group」不會變成一個組織實體。

### REST API 收集不會產生文件

**現況：** REST API connector 把遠端回應存成一筆原始證據，但**不拆成文件**。後續的正規化、實體抽取、搜尋索引都建立在文件上，所以這條路徑收進來的資料不會出現在文件列表、搜尋結果，也不會抽出組織實體。

**影響：** 不能把 REST API 當成「會自動變成可搜尋情報」的來源。要從 JSON／CSV 產生文件，請改走 [手動匯入](../usage/import.md)。

**替代做法：** JSON／CSV 匯入、RSS／Atom、靜態網頁、STIX 匯入都會產生文件。RSS 的 feed 標題、網頁的 `og:site_name`、匯入的 `publisher`（及 `vendor`／`organization` 等別名）會寫進文件屬性並抽出成組織實體。文章內文裡提到的組織名仍然不會被自動識別（見上一節）。

## 去重的範圍

### 改寫過的轉載不會被歸成重複

**現況：** 去重會抓「內容相同」和「幾乎一字不差」的文件（例如只改了標點、多了一段頁尾）。「語意相似」的比對預設是關閉的：實測發現它會把不同的文章誤判成同一篇，在找到可靠的判斷方式之前不開啟。

**影響：** 同一件事被不同媒體各自改寫報導時，每一篇都會是獨立的文件，搜尋結果裡會看到多篇。

### 版面相同的短文可能被誤判成重複

**現況：** 「幾乎一字不差」的比對看的是整篇文字。同一個網站的頁面如果有大段相同的導覽列、選單，而正文又很短，兩篇不同的文章可能被判成重複。實測有不同年份、不同主題的兩則短新聞被併在一起。

**影響：** 被判成重複的那篇不會出現在搜尋結果裡（原始資料仍保留）。匯入前先去掉網頁版面文字、只留正文，可以降低這種情況。

## 關鍵字搜尋的範圍

### 簡體與繁體：標題、摘要、正文已對齊

**現況：** 關鍵字搜尋在比對標題、摘要、正文之前，會把兩種字形折成同一套再查。搜「秦剛」可以找到只寫「秦刚」的文件，反過來也一樣。

**還沒涵蓋的：** 作者欄，以及實體名稱（用人名或組織名做實體過濾時）。這些仍只比對你輸入的字形，請兩種各查一次。另外，**只有一個中文字的詞**不互通：搜「罚」找不到只寫「罰鍰」的文件，請改打完整的詞。

**影響：** 標題、摘要、正文不再因為字形不同而整批漏掉。若結果明顯缺了某一種字形的文件，多半是那些文件還沒重建進搜尋索引，而不是比對規則又把簡繁分開。

## Discovery（發現新關聯）的範圍

### 只在已收集的資料裡尋找

**現況：** Discovery 在 Neo4j 關聯圖裡尋找與已知實體相關的目標。系統不會主動上網搜尋或呼叫外部情報 API。

**影響：** Discovery 找得到什麼，取決於系統已經收進來多少資料。如果一個相關目標從未出現在任何收集到的文件裡，Discovery 找不到它。

### 目前只往外看 1 層鄰居

**現況：** Graph Expansion 方法找的是目標實體在 Neo4j 裡的直接鄰居（1-hop），不做多層遞迴展開。

**影響：** 「A 認識 B，B 認識 C，所以 C 可能跟 A 有關」這類間接關聯，目前的 Discovery 找不到。

### 觸發點只有實體（Entity）

**現況：** 目前 Discovery 的起點是一個已存在的 Entity（透過 `POST /entities/{id}/discover` 或 `POST /discovery/run` 加 seed）。不能直接用文字關鍵字或集合（Collection）做為起點觸發 Discovery。

## AI 相關的限制

### Discovery 預算有一個欄位設定了但尚未生效

**現況：** `max_requests_per_run` 可以設定、會存進資料庫、API 也會回傳，但目前沒有任何 Discovery 方法會對外部發出 HTTP，所以這欄還沒接上。這**不是無限制**。`daily_ai_budget` 與 `max_ai_calls_per_run` 已在 AI 閘道對 Collection 帳戶生效；目前生產上的自動核准走系統帳戶，不消耗 Collection 額度，所以實際用量會是 0，直到有 Discovery 方法以 Collection 帳戶呼叫 AI。真正會被 Discovery 執行流程檢查的還有 `max_candidates_per_run`、`daily_request_budget`、`max_depth`。

**影響：** 把 `max_requests_per_run` 設成很小的值，也不會限制任何東西。把 AI 日額度設得很小，目前也不會擋住自動核准。要控制 Discovery 的規模，請用 `max_candidates_per_run` 與 `daily_request_budget`。查 `GET /api/v1/collections/{id}/budget` 的 `field_status` 可以看出哪一欄已生效。

### 資源壓力感知看的是推論請求本身，不是主機負載

**現況：** AI Gateway 會依近期延遲、HTTP 429／逾時／錯誤比例、以及排隊人數升高時降級低優先權請求。門檻尚未做容量測試；流量太少時維持「正常」。互動請求（P0）刻意不看這個訊號。主機 CPU／記憶體壓力還沒接上。

**影響：** 自動降級只在推論後端開始變慢或大量回錯誤時才會觸發。主機本身很忙但推論還很快時，這個機制不會動作。要手動控制 AI 並發量，調整設定檔裡的 `auto_approval.llm.max_concurrent`。

## 語意搜尋（向量搜尋）

### 語意搜尋需要先部署向量模型

**現況：** 語意搜尋和混合搜尋依賴 OpenSearch ml-commons 上部署的向量模型。這個模型不會自動安裝，需要執行 `scripts/opensearch-ml-setup.sh`（英文）或 `scripts/opensearch-ml-setup-e5.sh`（多語言）。

**影響：** 沒有部署模型時，語意搜尋的 API 呼叫會失敗。關鍵字搜尋不受影響。

### OpenSearch 重啟後需要重新部署模型

**現況：** OpenSearch ml-commons 的模型在重啟後需要重新載入（re-deploy）。這個過程需要手動執行，不是自動的。

**替代做法：** 如果不需要語意搜尋，關鍵字搜尋（包含布林、日期範圍、語言過濾）在任何狀態下都可用。

## 安全性

### Kafka 連線目前沒有 TLS 或 SASL 認證

**現況：** 服務與訊息佇列（Redpanda）之間的連線是明文，沒有傳輸層加密（TLS），也沒有身分認證（SASL）。用來連線的 Kafka 函式庫目前編譯時沒有開啟加密支援。

**影響：** 在同一個網路上的任何程式都可以連線到 Redpanda 端口，讀取或寫入事件。

**目前的替代做法：** 在網路層隔離（僅允許這些服務所在的主機存取 Redpanda 端口）。**正式環境部署前必須在網路層做隔離，或重新編譯加入 TLS/SASL 支援。**

### SQLite 後端的稽核記錄與 API Token 尚未實作

**現況：** 使用 SQLite 作為後端時（用於本機應用程式開發），`AuditLog` 和 `ApiTokenStore` 的持久化未實作（migration schema 已建立，但 store 層沒有對應的寫入邏輯）。Token 只在記憶體裡，服務重啟後失效。

**影響：** 這只影響使用 SQLite 的情境。使用 PostgreSQL 的正式部署不受影響。

## 維運可見性

### 稽核記錄與失敗事件沒有保留期限

**現況：** `audit_log` 表目前沒有任何自動刪除或封存機制，資料無限期保留。`auth.failed`（認證失敗）事件的寫入速率可被外部控制（例如大量嘗試登入）。`failed_events` 同樣不自動清——清掉就丟失可重放的原始事件內容。

**影響：** 長期運行後 `audit_log` 與 `failed_events` 會持續增長，需要手動維護。

**目前替代做法：** 定期手動清理超過特定日期的稽核記錄，或限制服務的公開存取。不要清 `failed_events` 除非已經確定不需要重放。

### jobs 保留期限只涵蓋 collect 終態

**現況：** `[retention.jobs]` 會定期刪除 `collect` 類型、已結束（completed／failed／cancelled）且超過保留天數的 Job。預設 completed／cancelled 7 天、failed 30 天。其他類型（STIX 匯出、圖重建等）不會被排程刪。

**影響：** 長期運行後非 collect 的 Job 紀錄仍會持續增長。手動清除可用 `POST /api/v1/ops/jobs/purge`（admin）。

### 物件儲存健康檢查只確認閘道存活

**現況：** SeaweedFS 的健康檢查（`GET /status`）只確認 S3 閘道的 HTTP 端口有人接，不驗證底層的 filer 或 master 服務是否存活——這個端點固定回 200。

**影響：** 健康檢查全綠不代表物件讀寫正常。若 filer 已掛，上傳原始證據的請求會失敗，但健康狀態仍顯示為健康。

**確認物件層是否真的可用：** 實際匯入一筆資料，確認回應成功且查得到。

## 背壓與資料流控

### 下游積壓會讓收集器降速；主機壓力與 AI 壓力尚未接上

**現況：** 收集器會查正規化服務在 `raw.collected` 上的積壓。積壓到門檻時本輪併發降為 1；再高就本輪不派新工作（被略過的連接器狀態不變，下一輪到期會再排到）。查詢失敗或逾時照常收集，不擋資料進來。

監控指標 `osint_queue_depth` **仍然只有人寫、沒有人讀**——收集器看的不是它。

**還沒做的：** 主機 CPU／記憶體／磁碟壓力、以及 AI 的資源壓力訊號。那些歸後續的 Resource Guard，目前不會讓收集器因主機忙碌而放慢。

**門檻是推測值。** 預設「降速 5000、暫停 50000」沒有做過容量測試。調整前請先看收集器 `/metrics` 的 `osint_collector_downstream_lag` 實際分佈。設定在 `[collector.backpressure]`。暫時關掉：`enabled = false`。

### 收集失敗的連接器會拉長重試間隔，但第一次同時失敗時仍會全派

**現況：** 連接器連續失敗後會指數退避（預設第一次等 5 分鐘，上限 12 小時），每一輪最多只重試 8 個失敗中的連接器。正常的連接器不再被失敗重試拖住。每一次嘗試仍會留下一筆工作紀錄。

**影響：** 大量連接器**第一次**同時失敗時（失敗次數都還是 0），退避與每輪上限都還沒開始算，第一輪仍會全部去試；第二次起才生效。工作紀錄沒有自動清除期限：實測曾累積約 416 萬筆失敗紀錄、佔約 1 GB。

**目前替代做法：** 確定修不好的連接器請停用（`PATCH /api/v1/connectors/{id}` 設 `enabled: false`）。來源修好後，可用 `POST /api/v1/ops/connectors/{id}/reset-backoff` 立刻重試，不必等退避結束。

### 收集服務停止時會等進行中的工作；其他服務處理完手上那一則就停

**現況：** 收集服務收到停止訊號後，會先停止接新工作，再等待進行中的收集結束（預設最多 20 秒）；等不及才中斷。中斷的工作會標成「已取消」，連接器回到閒置，失敗次數不加。若被強制終止，下次啟動會把卡住的執行中工作標成失敗。其他服務收到停止訊號後，會處理完手上那一則事件再結束；關聯圖重建這類長工作會在批次之間停下，工作標成失敗，下次啟動時也會回收卡住的工作。

**影響：** 一般停止在一秒內完成，不會被強制終止。被中斷的關聯圖重建要重新觸發。

## 事件

### 發現引擎的事件已發送，但還沒有消費者

**現況：** 八種事件（`seed.created`、`candidate.created`／`approved`／`rejected`、`discovery.completed`、`ai.requested`／`completed`／`failed`）已由 API 與 worker 寫進 transactional outbox，再由 `osint-api` 背景郵差送到 Redpanda。`seed.updated` 與 `discovery.requested` **刻意不發**（沒有更新種子的 API；派工已由 `job.dispatched` 覆蓋）。目前還沒有服務訂閱這八個主題。

**影響：** 訂閱這八個主題可以收到事件；自動收集、回饋循環仍要等後續版本接上消費者。`seed.updated`／`discovery.requested` 永遠不會出現，不要訂它們。

## 段落（Chunk）

### 段落已切好，但還沒有段落向量，也還不能用段落檢索

**現況：** `osint-chunk-worker` 會把每份非重複文件切成段落存起來，並發出 `document.chunked` 事件。段落向量化與段落檢索 API 是下一階段的工作，目前還沒有服務訂閱這個事件，搜尋仍以整份文件為單位。

**影響：** 長文後半段在語意搜尋裡仍然找不太到（整份文件只有一個向量，模型一次最多讀 512 個 token）。

### 網頁與長篇報告目前用固定長度切段

**現況：** 設計上網頁與長篇報告要依語意切段，目前先依句子打包成約 300 token、前後重疊約 100 token 的段落。匯入資料一筆一段，RSS 條目整篇一段；超過模型上限時才在文件內部再切開。

**影響：** 段落邊界可能落在主題轉換的中間。語意切段要等評估題組量過效益再開。

## 資料完整性的已知邊界

### STIX 匯出對關係超過 100 條的實體會靜默略過部分關係

**現況：** STIX 匯出時，每個實體最多只取 100 條關係。任何一個實體若參與超過 100 條關係，匯出時只會取前 100 條，多出來的靜默略過，不會報錯。

**影響：** 核心關聯超過 100 條的高度連結實體（例如知名 CVE）在 STIX 匯出時，接收方只會看到部分關係。

## Collection 的歸屬

### 把來源加進集合，不會回填已經落地的舊資料

**現況：** 一筆原始證據可以同時屬於多個調查集合（`raw_evidence_collections`）。收集時會把來源 ∪ 連接器目前掛上的集合寫進去；匯入時可用 `collection_ids` 指定，省略則用來源目前掛上的集合。之後才把來源／連接器加進另一個集合，**只影響之後收進來的資料**，不會回頭改已經落地的歸屬。

**影響：** 「這個來源現在屬於這個調查」不等於「這個來源過去收進來的每一筆都屬於這個調查」。那是刻意的：回填等於改寫歷史歸屬，會讓「這筆資料當時屬於哪個調查」變得不可信。

**替代做法：** 若要把舊資料納入新調查，請另外匯入或重新收集。集合建立後可用 `POST /api/v1/collections/{id}/sources` 與對應的連接器端點增減關聯。

### 一個來源／連接器最多屬於 50 個集合

**現況：** `POST /collections`（帶 `source_ids`／`connector_ids`）與 `POST /collections/{id}/sources`、`POST /collections/{id}/connectors` 在寫入任何關聯之前，會檢查每個來源／連接器目前掛了幾個集合。已掛上的重送算冪等、不會被擋；要新增且已達 50 個則整筆 422，已寫入的關聯不會被改。

**原因：** 收集時取來源∪連接器目前掛上的集合，兩邊各最多讀 100 筆。寫入端把每邊卡在 50，聯集最多 100，等於讀取上限，才不會再靜默截掉第 101 個。

**影響：** 一個來源不能同時出現在第 51 個調查集合。請先從較不相關的集合拿掉它（`DELETE /api/v1/collections/{id}/sources/{source_id}`，連接器則是 `.../connectors/{connector_id}`）。

**已知限制：** 兩個並發請求可能同時通過檢查而讓實際數量略超過 50。要讓聯集超過 100 需要大量並發；這是已知、可接受的競態。
