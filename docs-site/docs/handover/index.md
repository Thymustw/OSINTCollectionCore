# 接手開發

這一章寫給**要接手開發這個專案的人**：懂技術、會讀程式，但沒參與過先前的開發。

!!! note "本章會直接提到原始碼結構"
    其他章節是產品文件，刻意不談內部實作。這一章不一樣：會直接寫 crate（Rust 的套件單位）
    名稱、原始碼路徑、trait（Rust 的介面定義）名稱與事件 topic（訊息主題）名稱。
    如果你只是要使用這套系統，可以跳過這一章，從[快速上手](../getting-started/quickstart.md)開始。

---

## 讀完這一章你應該能

| 目標 | 在哪一頁 |
|---|---|
| 知道 35 個 crate 各做什麼、從哪一個讀起 | [原始碼地圖](codebase.md) |
| 知道改一個功能要動哪些檔案、哪裡容易漏 | [改一個功能要動哪些地方](change-guide.md) |
| 知道現在做到哪個版本、欠了什麼、下一步往哪走 | [版本路線與未修清單](roadmap.md) |

## 建議閱讀順序

| 順序 | 讀什麼 | 為什麼 |
|---|---|---|
| 1 | [快速上手](../getting-started/quickstart.md) | 先親眼看過資料從匯入到上圖的完整過程，後面的東西會好讀很多 |
| 2 | [系統架構](../architecture/overview.md)、[資料流](../architecture/data-flow.md) | 知道 10 個服務怎麼透過事件串起來 |
| 3 | [設計原則](../architecture/principles.md) | 這個專案的限制大多是刻意的；不懂原則會把設計當成 bug 去修 |
| 4 | [原始碼地圖](codebase.md) | 把服務對應到實際的 crate 與目錄 |
| 5 | [版本路線與未修清單](roadmap.md) | 動手之前先知道哪些坑已經被記錄過 |
| 6 | [改一個功能要動哪些地方](change-guide.md) | 真的要改東西時，照這頁的清單逐項檢查 |

## 怎麼用這一章發問

每一頁都切成小節，**每個小節標題就是一個可以直接拿來問的單位**。
發問時指明頁面與小節，比描述「那個講 migration 的地方」精準得多。例如：

| 問法 | 指向 |
|---|---|
| 「原始碼地圖的『儲存介面與實作』，`storage-core` 和 `storage-postgres` 的分工是什麼？」 | [原始碼地圖](codebase.md) 的一個小節 |
| 「改一個功能要動哪些地方的『新增或修改資料表欄位』，為什麼只加 SQL 檔不夠？」 | [改一個功能要動哪些地方](change-guide.md) 的一個情境 |
| 「版本路線的『V0.4 前置整備』，背壓那一項要做到什麼程度才算完成？」 | [版本路線與未修清單](roadmap.md) 的一個小節 |

每個小節開頭的連結圖示（滑鼠移到標題上會出現）可以複製該小節的網址，直接貼進問題裡。
