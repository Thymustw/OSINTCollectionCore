# 版本路線與未修清單

這一頁說明專案的版本路線、目前做到哪裡、下一步建議怎麼走，以及已知但還沒修的問題。

---

## 版本路線

版本必須依序完成，每一版通過驗收才進下一版。每一版的完整規格在 repo 的 `docs/specs/SPEC_V0.x.md`。

| 版本 | 主題 | 一句話目標 | 狀態 |
|---|---|---|---|
| V0.1 | 資料地基 | 資料進得來、存得住、可去重、可搜尋、可回溯 | 完成 |
| V0.2 | 情報地基 | 從「資料平台」升級成「情報平台」：實體解析與合併、關聯圖、時間軸、向量與語意搜尋、STIX 2.1 匯入匯出 | 完成 |
| V0.3 | 發現地基 | 根據已有的證據主動找下一步，而不是只等人工輸入：種子（Seed）、候選（Candidate）、AI Gateway、Discovery、預算控管 | 完成（部分規格項目未逐字滿足，見下方未修清單） |
| V0.4 | 自動化與智慧化地基 | 建立持續運轉的情報循環：發現 → 驗證 → 收集 → 觀察 → 偵測 → 關聯 → 告警 → 再發現 | **未開始** |
| V1.0 | 正式上線核心 | 不以新功能為主，而是讓核心能長期運作：可備份還原、可升級、可監控、可被多個應用穩定依賴 | 未開始 |

**現在的位置：** V0.3 完成，V0.4 尚未動工。建議先做下方的「V0.4 前置整備」再開工。

### V0.4 要做什麼

摘自 `docs/specs/SPEC_V0.4.md`：

| 模組 | 一句話說明 |
|---|---|
| Policy Engine（政策引擎） | 決定一個來源能不能收、能不能自動收、保留多久、能不能轉發；任何自動加入來源的流程都要先過它 |
| Automated Collection（自動收集） | 已核准的候選來源自動建立來源、連接器與排程，全程留稽核紀錄 |
| Adaptive Scheduling（自適應排程） | 依來源優先權、更新頻率、近期活躍度、可靠度、過去錯誤調整收集間隔，但不能突破限速與政策 |
| Source Intelligence（來源評分） | 每個來源的可靠度、可信度、原創性、活躍度等分數，每個分數都要能解釋 |
| Signal（訊號） | 還不足以構成確定事件、但值得追蹤的跡象（例如可疑的 commit、新的漏洞利用程式提及） |
| Event Detection（事件偵測） | 從文件、訊號、實體、時間軸偵測事件，並管理事件的生命週期（候選 → 觀察 → 佐證 → 確認 → 結束） |
| Event Evidence（事件證據） | 多篇報導同一件事要聚合成「1 個事件 + N 筆證據」，而不是 N 個事件 |
| Correlation Engine（關聯引擎） | 依時間接近、實體重疊、語意相似、圖距離、來源獨立性等因素把事件與訊號歸群，並附解釋 |
| Trend（趨勢）與 Baseline（基準線） | 和 7／30／90 天基準比較，偵測提及量、來源多樣性等的顯著上升；不能只看絕對數量 |
| Alert（告警）與 Alert Dedup（告警去重） | 依條件觸發告警；同一事件的多篇重複報導不能重複告警 |
| Feedback Loop（回饋循環） | 新事件 → 相關實體 → 再 Discovery → 新來源 → 新證據；要有遞迴與預算防護 |
| Graph Analytics（圖分析） | 度數、中心性、共同鄰居、連通元件、社群偵測、時序圖分析 |
| Automation Safety Controls（自動化安全控制） | 深度、每日請求、每日候選、自動來源數、AI 成本等上限，以及來源與網域黑名單 |
| Kill Switch（總開關） | 一個執行期可切換的開關，關閉後停止自動發現與自動擴張收集，但搜尋與既有資料存取照常 |

規格另外要求 V0.4 對 AI 負載做到：每個集合的 AI 配額、每個優先權的佇列配額、全域佇列上限、同時推論上限、低優先權工作在壓力下自動暫停，以及**自動化背壓**——「發現更多工作」只能變成「更多排隊中的工作」，不能直接變成「更多同時進行的模型請求」。

## V0.4 前置整備

**建議不要直接開工 V0.4。** 理由不是「還有 bug」，而是有幾個缺口會讓 V0.4 的驗收**從設計上就過不了**，另外幾個會被自動化放大。

### 會讓 V0.4 驗收過不了的三項

| 缺口 | 為什麼擋住 V0.4 |
|---|---|
| **背壓** | 下游塞車時收集器不會自動放慢；AI 的資源壓力訊號永遠回報「正常」。V0.4 規格明確要求自動化背壓、壓力下暫停低優先權工作、佇列飽和時告警——現在沒有任何訊號可以驅動這些行為 |
| **AI 配額** | Discovery 預算裡的 AI 相關配額（每次執行與每日的 AI 呼叫上限）設了不會生效。V0.4 要求每個集合的 AI 配額能防止單一集合獨佔模型，這需要配額真的會被消耗與檢查 |
| **事件發送** | V0.3 定義的 10 種事件（`seed.created`、`candidate.approved` 等）沒有任何程式發送。V0.4 的自動收集、回饋循環都要靠「候選被核准」「Discovery 完成」這類事件觸發下一步；沒有事件，自動化就沒有起點 |

### 會被自動化放大的兩項

| 缺口 | 為什麼自動化後會變嚴重 |
|---|---|
| **重複候選** | 對同一實體重跑 Discovery 會產生重複候選。人工觸發時只是清單有點亂；自動化反覆觸發後，重複候選會成倍累積，每一筆還可能被自動建成來源 |
| **URL scheme 沒驗** | 核准候選時只驗 URL 格式、不驗 scheme，`javascript:`、`data:` 這類網址會通過。人工核准時還有人看；自動核准、自動建連接器後就沒人看了 |

另外，「收集失敗沒有退避」與「collector 不能優雅停止」在 V0.4 自動建立大量連接器後會直接影響排程效率與部署穩定度，也建議一併處理（見下方清單）。

## 未修清單

每一條寫的是：問題是什麼、會造成什麼影響、建議什麼時候處理。

### V0.4 開工前必須先處理

| 問題 | 影響 | 建議時機 |
|---|---|---|
| 收集失敗的連接器**每一輪都重試**，沒有「連續失敗就延後下次嘗試」的機制 | 實測數千個壞掉的連接器時，一輪排程約要 7 分鐘，正常的連接器被拖慢。每次嘗試都會寫一筆工作紀錄：開發環境清空前實測工作紀錄表有約 416 萬筆失敗紀錄、佔約 1 GB（整個資料庫約 1.1 GB） | V0.4 前（自適應排程的前提） |
| collector 收到停止訊號後 10 秒內不會結束，被容器平台強制終止 | 進行中的收集被硬切；部署或重啟時無法乾淨地停下 | V0.4 前 |
| 匯入時沒有 `url` 又用相同檔名，**內容不同也會被當成重複** | 被判成重複的文件不抽實體、而且沒有錯誤訊息，資料看起來匯入成功但什麼都沒抽到 | V0.4 前 |
| 對同一實體重跑 Discovery 會產生**重複候選** | 候選清單出現重複項目；自動化後會成倍累積 | V0.4 前 |
| 核准候選時 URL **只驗格式不驗 scheme** | `javascript:`、`data:` 這類網址可以通過核准 | V0.4 前 |
| Discovery 預算的 `max_requests_per_run`、`max_ai_calls_per_run`、`daily_ai_budget` 三個欄位**設了沒作用** | 可以設定、會存進資料庫、API 也會回傳，但沒有任何執行流程讀它們 | V0.4 前 |
| 下游塞車時收集器**不會自動放慢**；AI 的資源壓力訊號**永遠回報正常** | 積壓只能靠人工調設定；AI 依壓力降級的機制永遠不會觸發 | V0.4 前 |
| V0.3 定義的 10 種事件**宣告了但沒有程式發送** | 任何想訂閱這些事件的服務都不會收到東西 | V0.4 前 |
| **組織實體不出現在關聯圖上** | 從發布者欄位抽出的組織查得到，但在 Neo4j 圖上看不到。根因還沒查；推測是組織只和文件有關係（「文件由某組織發布」），而圖只投影兩端都是實體的關係 | V0.4 前（先查清根因） |
| 一次把多個來源加進集合**不包在同一筆交易** | 中途失敗會留下「加了一半」的關聯 | V0.4 前 |
| 失敗事件紀錄的寫入路徑**沒有端到端驗證**；`core-events` 的 Redpanda 往返測試在本機一直失敗 | 不確定失敗事件真的會被記下來；整個 workspace 沒有一份乾淨全綠的測試基準，新的失敗容易被既有失敗掩蓋 | V0.4 前 |

### 安全與資源（有期限）

| 問題 | 影響 | 建議時機 |
|---|---|---|
| 服務與 Redpanda 之間**明文、無認證** | 同網路上任何程式都能讀寫事件 | **V1.0 前必修**；在那之前要靠網路隔離 |
| 稽核紀錄與失敗事件紀錄**沒有保留期限** | 兩張表無限增長；認證失敗的稽核寫入速率可被外部控制 | V1.0 資料保留功能 |
| 物件儲存的健康檢查**只確認閘道活著** | 底層儲存掛了，健康檢查仍是綠燈 | V1.0 前 |
| STIX 匯出**每個實體只取 100 條關係**，多的靜默略過 | 高度連結的實體匯出後，接收方只看到部分關係，沒有任何提示 | 匯出功能正式化時（V1.0） |
| 會呼叫 AI 的程式持有**完整的資料庫寫入權限** | AI 相關程式出問題時，影響範圍是整個資料庫 | V1.0 正式環境安全強化 |
| 相依套件有幾項安全公告被列為**暫時例外** | 例外有到期日，到期前要重新評估 | **2026 年 12 月中**複審（清單在 `deny.toml` 與 `docs/security/VULNERABILITY_TRIAGE.md`） |
| 每個來源／連接器最多屬於 50 個集合，但上限檢查有**並發競態** | 大量並發請求時實際數量可能略超過 50 | 可接受，暫不處理 |

### 功能缺口

| 問題 | 影響 | 建議時機 |
|---|---|---|
| 維運中心看不到 AI 排程與佇列狀態，也沒有暫停／恢復 AI 工作的操作 | AI 負載只能從設定檔調整，執行中看不到也控制不了 | V0.4（自動化會大幅增加 AI 負載） |
| 沒有依 context 長度（單次送給模型的文字量）排程 | 長短請求混在一起，無法依成本分流 | V0.4 |
| AI 的長時間負載與重啟後恢復**沒有測過** | 不知道持續高負載或模型服務重啟後系統的表現 | V0.4 |
| AI 輸出沒有結構化 schema 約束 | 模型回傳格式只能事後解析，格式錯誤時只能當失敗 | V0.4 |
| Discovery 只看 **1 層鄰居**、只能**從實體出發** | 找不到間接關聯；不能用關鍵字或集合當起點 | V0.4 回饋循環時一併擴充 |
| **沒有網頁操作介面** | 全部操作靠 API 或命令列 | 規格每一版都列了操作介面，目前一個畫面都沒做；何時做需要另外決定 |
| **領域事件表沒有寫入者** | 事件資料表與 API 存在，但沒有任何流程會自動產生事件；V0.4 的事件偵測要從這裡接 | V0.4 |
| **集合時間軸 API 不存在** | 只有實體時間軸，沒有以調查集合為單位的時間軸 | V0.4 |
| SQLite 後端**不存稽核紀錄與 API token** | 用 SQLite 時 token 只在記憶體裡，重啟就失效 | 有人要用 SQLite 部署時 |
| **外部密鑰儲存**沒有實作 | `SecretRef` 的 `store:` 寫法能通過驗證，但解析時一律失敗；目前只能用環境變數或檔案 | V1.0 正式環境安全 |
| **語意搜尋沒有進 CI** | CI 環境沒有向量模型，這條路徑只在本機測過 | V1.0 CI／CD |
| 混合搜尋的 6 個權重有 **4 個沒作用** | 實體比對、新近度、來源分數、信心度四個權重沒有實作；設成非 0 時服務啟動會發警告 | 有排序需求時 |

### 刻意不做／設計限制

這些不是待修的 bug，是經過決定的取捨。改變它們之前先理解為什麼。

| 項目 | 為什麼這樣 |
|---|---|
| REST API 連接器收集的內容**不產生文件** | 任意 JSON 沒有欄位對映就無從拆解。要把 JSON 變成文件請走匯入（可以指定欄位對映） |
| 把來源加進集合**不回填舊資料** | 回填等於改寫歷史歸屬，會讓「這筆資料當時屬於哪個調查」變得不可信 |
| **不從內文辨識人名與組織名** | 實體抽取只用確定性規則；人名與組織只從結構化欄位（作者、發布者）取得 |
| **文件不是圖上的節點** | 圖只放實體與實體之間的關係；文件與實體的關係存在 PostgreSQL，查得到但不上圖 |
| AI 可以在**中間信心帶**直接觸發實體合併 | 這是「AI 輸出不能直接覆寫身分判定」原則的唯一刻意例外，已經裁決過；合併可以復原。要再開其他例外必須另外決定 |
